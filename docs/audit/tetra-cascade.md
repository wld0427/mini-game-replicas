# 功能审计报告 — Tetra Cascade 无尽方块

> 审计日期：2026-11-28 · 审计范围：`games/tetra-cascade/`
> 方法：README 承诺逐条核对 → 源码比对 → 逻辑层穷举脚本 → Chromium 真实驱动页面
> **审计时测试 42/42 全绿** —— 即以下全部是「测试通过但游戏有洞」的问题。
> 本文件只记录问题，修复由后续轮次按 `docs/process/README.md` 的四道门禁执行。

## 总体判断

**有 P0 机制缺陷**：`I` 块竖着贴在最右列时**旋转不了**，玩家在该位置彻底卡死；
而 README 明确承诺「贴边旋转会被踢墙救回」。

**锁定延迟的时序与承诺不符**：README 说「落地后有 0.5s 缓冲，期间可微调位置」，
实际落地判定要等下一拍重力（1 级 1000ms），落地后最多要 **1.5s** 才锁定，
而且那 1s 里方块还没被标记为「已落地」，**玩家的微调不���续命**，锁定时间照走。

上下文规则、7-bag、暂存、图鉴里程碑、成就、存档脏数据回退等其余部分经穷举验证**是完整的**。

## A. 机制失效（P0，本轮必修）

| 编号 | 功能 | 问题 | 证据 | 建议 |
| --- | --- | --- | --- | --- |
| A-1 | 旋转踢墙（README：「贴边旋转会被踢墙救回」） | **`I` 块贴最右列时旋转彻底失败**。踢墙表 `KICKS = [0, -1, 1, -2, 2]` 最大只平移 2 列，而 `I` 块横放要占 4 列（起点必须 ≤ 6 列）。竖放贴右墙（x = 9）时需要 **-3** 的踢墙量，表里没有 → `tryRotate()` 全部试完仍失败 | `assets/data.js:141`（`KICKS`）；`src/logic.js:330`（`tryRotate`）。**穷举证据**：空棋盘上把 `i` 竖放在 x = 9，顺时针旋转返回 `false`；`i` 的 rot1 / rot3 贴右墙均失败（其余 54 种组合均能救回） | 踢墙表补到 ±3（`[0,-1,1,-2,2,-3,3]`），并同步 README 的表述；补一条「每种方块每个旋转态贴左右墙都能旋转」的穷举用例守住 |

## B. 体验缺陷（P1，本轮必修）

| 编号 | 功能 | 问题 | 证据 | 建议 |
| --- | --- | --- | --- | --- |
| B-1 | 锁定延迟（README：「落地后有 0.5s 缓冲，期间可微调位置」） | **落地判定被绑在重力节拍上**。`tick()` 只在 `gravityAcc >= interval` 时才检测方块是否触底（1 级是 1000ms 一拍），于是「落地」到「判定为落地」之间最长有 1s 的空窗：这段时间 `grounded` 为 false，`resetLock()` 直接 return —— **玩家的微调不算续命**，锁定时间照旧 | `src/logic.js:468`（`tick`）。**实测**：落地判定用 1008ms，落地后 496ms 锁定，**总缓冲 1504ms**，与承诺的 500ms 差 3 倍 | 每帧独立检测落地（方块下移会撞就置 `grounded`），让锁定延迟从「真正落地」那一刻起算；补一条「落地后 500ms ± 120ms 内锁定」的用例 |
| B-2 | 首屏棋盘可见性 | **首屏看不到棋盘**。菜单遮罩是 `rgba(8,10,18,0.82)` + `backdrop-filter: blur(3px)`，整块 609px 高的棋盘被压在下面，玩家打开游戏看到的是一块空深色矩形，网格线一点都读不出来 | `assets/app.css:291`（`.overlay`）。**浏览器实测**：遮罩不透明度 0.82，`overlayCovers = true`（完全覆盖棋盘） | 菜单态的遮罩改为半透明（棋盘透出）或把标题卡移到棋盘外；游戏进行中与结束态保持现在的压暗效果 |
| B-3 | 首屏「下一个」预览 | **首屏「下一个」那一栏整个是空的** —— `renderNext()` 在没有对局时直接 return，连占位框都没有；旁边的「暂存」却有框，两边不对称，看起来像少渲染了一块 | `assets/app.js:299`（`if (!game) return;`）。**浏览器实测**：首屏 `#next-box` 子节点数 = 0，而 `#hold-box` 有 16 个小格 | 首屏也渲染 3 个空的预览格（或一个明确的「—」占位） |

## C. 一致性 / 打磨（P2）

| 编号 | 项 | 问题 | 证据 | 建议 |
| --- | --- | --- | --- | --- |
| C-1 | 消行计分（README：「连消额外 50 × 连击 × 等级」） | **一串连消里的第一次也拿到了连消奖励**。`lockPiece()` 里 `game.combo += 1` 在计分之前，于是首次单行消行得到 100×等级 + 50×1×等级 = 150×等级，而 README 的「连消」指的是连续消行的追加部分 | `src/logic.js:425-431`。**实测**：首次单行消行得 150（应 100）；第二次连消得 400 = 100×2 + 50×2×2 ✓ | 连击奖励用「本次消行之前的连击数」计（即 `combo - 1`），或把 `combo += 1` 移到计分之后；README 与实现取其一即可 |
| C-2 | HUD 过程统计 | **抛竿次数从不展示**。逻辑层记 `stats.casts`，界面 HUD 只有 分数 / 等级 / 行数 / 连击 | `src/logic.js:112` 附近记 `casts`；**浏览器实测**：HUD 的四项是「分数 / 等级 / 行数 / 连击」 | HUD 补一格「抛竿」；属增强项，不阻塞核心玩法 |
| C-3 | 档案往返 | **不是问题**：仅 `achievements` 对象的键序不同（`i:first` 排前 vs 排后），**无字段丢失** | 逐字段比对确认 | 无需改动，仅记录以免下轮误判 |

## E. 审计侧的环境事实

- headless Chromium 的 rAF 只有几帧/秒，浏览器断言**不能靠固定 sleep**，要用 `waitForFunction` 轮询。
- 计算样式的透明度判断：`rgb(r,g,b)` 没有 alpha 分量即**不透明**，只有 `rgba()` / `color(srgb ... / a)` 才带 alpha；
  按「分量数 ≥ 4 才取 m[3]」的写法会把不透明色误判成透明（本次审计中就踩了这个坑）。
