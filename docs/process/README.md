# 开发流程总纲（四道门禁）

> 本文件是 `mini-game-replicas` 仓库的**强制流程**。
> 定时任务每轮必须按此流程走，任何一道门禁不过，**不允许进入下一道，更不允许开始下一款游戏**。

## 为什么要有这套流程

早期 6 款游戏在"没有立项评审、没有设计文档、没有功能清单"的条件下产出，
结果是：**README 里承诺的功能，代码里没有实现；实现了的功能，UI 上玩家用不到；
实现了但没有测试的功能，改一行就悄悄坏掉**。
质量问题的根源不是"写得不够快"，而是**没有任何一份可逐条核对的清单**。

所以本流程的核心只有一个机制：
> **每一项承诺的功能，都必须同时留下「设计文档条目 → 代码实现标记 → 测试断言」三处痕迹，
> 少一处，机器判定为未完成，门禁不放行。**

这不是形式主义：它把"我觉得做完了"变成"机器能证明做完了"。

## 四道门禁

```
   ① 立项评审  ──通过──▶  ② 设计文档 + 开发计划  ──通过──▶  ③ 实现  ──通过──▶  ④ 交付验收
     (gate-proposal)          (gate-design)                      (gate-impl)        (gate-accept)
         │                        │                                  │                    │
   为什么做/亮点/差异化      功能清单(F-ID)/状态机/边界         代码审查+功能审查      全量测试+追溯矩阵
   评分 ≥ 阈值 + 无否决项   验收标准可判定/阶段有门禁          追溯矩阵无孤儿      视觉打磨验收
         │                        │                                  │                    │
         └──── 不通过 → 说明理由并放弃/换候选，不允许"先做着看" ────────────────────────────┘
```

### ① 立项评审（gate-proposal）

**目的**：在写第一行代码前，判断"这款游戏值不值得做"。

每款游戏必须先有一份 `games/<slug>/docs/proposal.md`，包含：

| 章节 | 必须回答的问题 |
| --- | --- |
| 一句话定位 | 这是什么游戏，玩家一句话能说清吗 |
| 为什么做它 | 上游/同类做法的**不足**在哪，我们补什么 |
| 核心亮点 | 最有辨识度的 1–2 个机制，说清楚"爽在哪" |
| 独特玩法 | 有没有同类里少见的机制（不是换个皮） |
| 表现力 | 视觉/动效/音效能不能撑起这个题材 |
| 差异化 | 与候选池里其他候选、与已有 6 款的区别 |
| 可测性 | 核心玩法能否用确定性逻辑表达并被单测覆盖 |
| 风险与代价 | 最可能做砸的地方，准备怎么兜底 |
| 评分 | 按 rubric 打分，总分 ≥ 阈值且无否决项才放行 |

**否决项（一票否决）**：核心玩法不可测 / 只是给已有游戏换皮 / 与仓库已有游戏高度重复 /
无法在无外部素材前提下做出可辨识的表现力。

> 评审必须**独立于实现**：立项文档写完后，先自查"如果没有这段代码，我还会选它吗"，
> 再用 `scripts/design-review.mjs` 做机器校验。机器校验只能查格式与红线，
> **"值不值得做"是人的判断，必须写进文档并署名**。

### ② 功能设计文档 + 开发计划（gate-design）

**目的**：把"亮点"翻译成**可逐条核对、可逐条验收**的工程规格。

`games/<slug>/docs/design.md` 必须包含：

- **功能清单表**：`| ID | 功能 | 说明 | 验收标准 |`，ID 形如 `F-001`，连续编号
- **状态机 / 数据结构**：核心状态怎么流转、数据怎么存
- **边界与异常**：空数据、超界输入、脏存档、无解状态分别怎么表现
- **交互流程**：玩家从进入到结束会依次经历哪些界面状态
- **打磨清单**：动画、音效、反馈、信息层级上要做的具体项（不能只写"优化体验"）

`games/<slug>/docs/plan.md` 是分阶段开发计划，每阶段必须写清：
**做什么 → 产出什么文件 → 验收命令与期望输出 → 该阶段完成的标准**。
阶段之间是串行门禁，前一阶段验收命令跑绿才允许开下一阶段。

### ③ 实现与代码审查（gate-impl）

- 核心规则必须落在 `src/logic.js`（不碰浏览器 API），否则无法确定性测试
- 每个功能在代码里留标记：`/** @feature F-001 */`
- 每个功能在测试里留标记：`/** @covers F-001 */`（或测试名以 `F-001` 开头）
- `scripts/review.mjs` 静态代码审查必须 0 问题
- `scripts/feature-trace.mjs` 追溯矩阵必须 0 缺口、0 孤儿

### ④ 交付验收（gate-accept）

交付前**全部**满足，缺一不可：

1. `node scripts/gate.mjs` 通过（静态审查 + 设计校验 + 追溯矩阵 + 全量测试）
2. 每个功能清单条目都有对应的**行为**断言（不是"函数存在"这种弱断言）
3. 至少 1 条**浏览器端冒烟**覆盖核心玩法链路，不只是首屏渲染
4. **视觉与交互打磨验收**：至少截 2 张图（桌面 + 移动）人工确认过，
   没有布局错位、遮挡、文字截断、按钮无反馈等问题
5. 部署后 `curl` 验证首页与关键资源返回 200
6. `docs/acceptance.md` 记录逐条验收结果（谁验的、怎么验的、结论）

### ⑤ 跨游戏约束（最重要的一条）

> **上一款游戏没有通过 `scripts/gate.mjs`，不允许开始下一款。**

质量优先于数量。宁可这一轮什么都不做，也不要堆一个半成品。
若某款反复做不达标准，应在 `docs/proposal.md` 里写明"评估后放弃"，并把候选退回候选池。

## 机器校验的能力边界

`scripts/gate.mjs` 能查的：文档结构是否齐全、功能 ID 是否双向对齐、测试是否覆盖、
代码是否有静态问题、测试是否真的绿。

它**查不了**的：这个游戏好不好玩、视觉够不够好看、亮点够不够亮。
所以**第 ① 步和第 ④ 步的视觉验收必须由人（或具备判断力的会话）实际看过**，
不能因为机器闸门全绿就宣布交付。
