# 功能设计文档模板

> 复制本文件到 `games/<slug>/docs/design.md` 后填写。
>
> **本文件里的「功能清单」是整个流程的基准**。
> `scripts/feature-trace.mjs` 会拿这里的每个 `F-xxx` 去代码里找 `@feature` 标记、
> 去测试里找 `@covers` 标记，三者对不齐就判定未完成。
>
> 规则：
> - ID 从 `F-001` 起连续编号，**不跳号、不重号**
> - 每个功能必须写**可判定的验收标准**（能被一条断言验证），禁止"体验流畅"这类无法判定的表述
> - 表以外的正文不算功能清单，不会被追溯校验覆盖

## 难度契约

<!--
**必填。**每个核心玩法都要能证明三档难度是分开的，否则说明难度没被设计过。

| 档位 | 必须成立 | 怎么验 |
| --- | --- | --- |
| 参考路线 | 一个「会玩的人」能稳定通关 / 达成目标 | 固定策略的输入序列驱动 `src/logic.js`，断言终局为成功 |
| 弱化路线 | 一个「水平一般的人」会挣扎或失败 | 显式给一条降级的输入序列（乱点 / 错点 / 只做最低限度操作），断言它**没有**轻松通关 |
| 挂机路线 | 一个「完全不操作的人」会明确失败 | 零输入驱动固定 tick 数，断言终局为失败（不能无限挂机得分） |

规则：
- 三条路线必须**用同一套规则代码**跑，不得为测试单独造一条"假逻辑"。
- 「弱化路线会失败」与「挂机路线会失败」是不同的断言，不能互相顶替。
- 随机触发类功能，弱化路线要写明**样本量**（如"200 局内至少失败 1 次"），
  而不是"可能会失败"这种不可判定的表述。
-->
